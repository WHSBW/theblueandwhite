## Architecture Overview

```
Reporter/Editor (browser)
        │  POST {action, path, content}
        ▼
Cloudflare Worker  ◄── GITHUB\_TOKEN secret (never in client code)
        │  PUT file via GitHub Contents API
        ▼
GitHub repo (WHSBW/theblueandwhite)
        │  GitHub Pages auto-builds on push
        ▼
blueandwhitewhs.com  ◄── reads articles list from Supabase (anon key)
```

The homepage and section pages are static HTML that run a small JS fetch against Supabase at load time to pull published articles. Individual article pages are static HTML files generated and pushed to GitHub by the Cloudflare Worker at publish time.

## The CMS (`cms/index.html`)

A self-contained \~1400-line vanilla JS single-page app. Uses the Supabase anon key directly (auth is custom — not Supabase Auth).

### CMS user roles

|Role|Can do|
|-|-|
|Reporter|Write articles, save drafts, submit for review, view own articles|
|Editor|Everything Reporter can do + review queue, publish/return articles|
|Adviser|Everything Editor can do + Staff Manager, Assignments, All Articles, delete|

Laura is the Adviser. Students are Reporters (potentially Editors for section editors).

### Publish flow

1. Reporter writes → fills headline + section + body (+ optional dek, photo URL, caption, credit) → **Save Draft** or autosave handles it
2. Reporter hits **Submit for Review** → status becomes `pending` → appears in editor Review Queue
3. Adviser/Editor opens Review Queue → clicks article → review pane opens with all fields pre-filled → can edit directly
4. Editor hits **Publish to Site** → CMS calls Cloudflare Worker with the generated HTML → Worker pushes to GitHub → GitHub Pages builds → article is live
5. Supabase record updated: `status = 'published'`, `github\_path = 'articles/{section}/{slug}.html'`
6. Homepage and section pages pick up the new article automatically on next load (they query Supabase for `status = 'published'`)

### Key CMS functions

|Function|What it does|
|-|-|
|`getArticlePayload(status)`|Builds the Supabase payload from current form values|
|`generateArticleHTML(article)`|Returns the complete HTML string for a published article page|
|`publishArticle()`|Reads rv- (review pane) fields, calls Worker, updates Supabase|
|`republishArticle(id)`|Re-publishes an archived article using current DB content|
|`archiveArticle(id, headline, githubPath)`|Deletes GitHub file + sets status to 'archived'|
|`deleteArticle(id, headline)`|Permanently deletes Supabase record (GitHub file already gone from archiving)|
|`doAutosave()`|Fires 3s after last keystroke; creates draft if new, updates if existing|
|`imgAlign(dir)`|Applies float/width inline styles to the last clicked body image|
|`openReview(id)` / `loadReviewArticle(id)`|Loads article into review pane|
|`loadAllArticles()`|Renders the All Articles management list|

### CMS form fields

**Writer pane (w- prefix):** `w-section`, `w-hed`, `w-dek`, `w-photo`, `w-body`, `w-caption`, `w-credit`, `w-assignment`

**Review pane (rv- prefix):** `rv-hed`, `rv-dek`, `rv-photo`, `rv-body`

## Photo Handling

**Lead photo URL field** — reporters paste a direct image URL (right-click image on any site → Copy image address). This URL:

* Renders as a full-width hero image above the article body on the article page
* Feeds the carousel slide background on the homepage
* Feeds the card thumbnail on section pages and homepage columns

**Body images** — reporters can paste images directly into the article body editor. Pasted images become base64-encoded HTML `<img>` tags embedded in the body HTML. These display fine on the article page but are too large to use in carousels/cards. For performance, resize large photos with squoosh.app before pasting.

**Image alignment toolbar** — click an image in the body editor (it gets a blue outline), then press:

* `← Img` — float left, 42% width, text wraps right
* `Img →` — float right, 42% width, text wraps left
* `↔ Full` — full width block, clears any float

Alignment styles are saved as inline styles with the body HTML.

## Recycle Bin & Auto-Takedown (added June 2026)

### What it does
- **Recycle Bin:** "Delete" no longer exists. Archived articles get a "♻ Recycle"
  button that sets `status = 'trashed'` and stamps `trashed_at`. Trashed articles
  appear in the CMS Recycle Bin view (editors + adviser) with Restore and Delete
  Forever buttons. Anything trashed 30+ days is permanently deleted automatically.
- **Auto-takedown:** The review pane has an optional "Auto-takedown" date field
  (with a +30 days shortcut). Saved to `takedown_at` on publish. When the date
  passes, the article is automatically removed from the live site and set to
  `archived` (still in the CMS, re-publishable). Blank = evergreen, never expires.

### How it runs
A **Cloudflare Cron Trigger** (`0 9 * * *` = 9:00 AM UTC / 4–5 AM Tampa, daily)
fires the `scheduled` handler in the Worker (morning-field-8e58). Each night it:
1. Finds `status = 'published'` rows with `takedown_at <= now` → deletes the
   GitHub file → sets `status = 'archived'`, clears `takedown_at`. If GitHub
   errors, it skips that article and retries the next night.
2. Finds `status = 'trashed'` rows with `trashed_at` older than 30 days →
   deletes the GitHub file if one somehow still exists → deletes the row.

### What it needed (already done — for rebuild reference)
- Supabase columns: `ALTER TABLE articles ADD COLUMN IF NOT EXISTS trashed_at
  timestamptz;` and the same for `takedown_at`.
- New article status value: `trashed` (alongside draft/pending/returned/
  published/archived).
- Worker secret `SUPABASE_SERVICE_KEY` = the Supabase **service_role** key
  (Supabase → Settings → API). The Worker talks to Supabase's REST API with it;
  it bypasses RLS, which is why it lives ONLY in Cloudflare, never in the CMS.
- Cron trigger added under Worker → Settings → Trigger Events.
- CMS (`cms/index.html`): Recycle Bin view, trash/restore/delete-forever
  functions, takedown date field in review pane, trashed articles excluded
  from All Articles, "comes down [date]" shown on scheduled articles.

### Troubleshooting
- **Publish button says "GitHub error: Requires authentication"** → the
  GITHUB_TOKEN secret is wrong/expired. Regenerate the token on GitHub,
  paste into the Worker secret, deploy. (Don't investigate; just re-mint.)
- **Nightly sweep not running** → check the Cron Trigger exists and the
  Worker deploy didn't remove the `scheduled` handler. Cloudflare →
  Worker → Logs shows scheduled invocations.
- **Article re-archived right after republish** → shouldn't happen
  (republish clears `takedown_at`), but if it does, check that column.
