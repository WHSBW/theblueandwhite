## Architecture Overview

```
Reporter/Editor (browser)
        │  login → Worker issues 12-hour session token
        │  POST {action, token, ...}
        ▼
Cloudflare Worker  ◄── secrets: GITHUB_TOKEN, SUPABASE_SERVICE_KEY (never in client code)
   │         │      ◄── Cron Trigger: 0 9 * * * (nightly sweep, 4–5 AM Tampa)
   │         │
   │         └── Supabase service-role REST calls (login, sessions, staff, sweeps)
   │
   │  PUT/DELETE files via GitHub Contents API
   ▼
GitHub repo (WHSBW/theblueandwhite)
        │  GitHub Pages auto-builds on push (CDN cache ≈ up to 10 min)
        ▼
blueandwhitewhs.com  ◄── reads published articles from Supabase (publishable/anon key)
```

The homepage and section pages are static HTML that run a small JS fetch against
Supabase at load time to pull published articles. Individual article pages and
staff.html are static files generated and pushed to GitHub by the Worker.

The Worker is the **auth gateway**: login happens there, and every privileged
action (publish, delete, staff management, staff page, password change)
requires a valid session token.

### ⚠️ Token expiry — ACTION REQUIRED by June 1, 2027

The GitHub token in the Worker is a fine-grained PAT (`newspaper-worker-2027`):
- Scope: WHSBW/theblueandwhite only
- Permission: Contents — Read and write
- Expires: **June 1, 2027**

When it expires, publishing silently stops working ("GitHub error: Requires

1. GitHub → Settings → Developer settings → Fine-grained tokens → Generate new
   token (same settings) — or Regenerate the existing one
2. Cloudflare → Worker → Settings → Variables and Secrets → update `GITHUB_TOKEN`
3. Delete the old token on GitHub
4. Update this section with the new expiry date

### Worker actions (POST JSON `{action, token, ...}`)

| Action | Who | What |
|---|---|---|
| `login` {student_number, password} | anyone | checks credentials server-side, returns 12-hour session token + safe user object (never password_hash) |
| `logout` | session | deletes the session row |
| `publish` {path, content, headline} | editor/adviser | PUT article file to GitHub (path must be `articles/…html`) |
| `delete` {path, headline} | editor/adviser | DELETE article file from GitHub |
| `publish_page` {page, content} | adviser | PUT a whitelisted page — currently only `staff.html` |
| `staff_list` | adviser | all users minus password_hash |
| `staff_add` / `staff_update` / `staff_remove` | adviser | roster management; remove detaches the user's articles (author_id → NULL) first so bylines survive and the delete succeeds; advisers can't be removed |
| `change_password` {current, next} | any session | verifies current, sets new |

### Nightly sweep (`scheduled` handler)
1. **Auto-takedowns:** published articles with `takedown_at <= now` → GitHub file
   deleted → status 'archived', takedown_at cleared. GitHub failure = skip and
   retry tomorrow.
2. **Recycle Bin purge:** `trashed` articles with `trashed_at` > 30 days old →
   GitHub file deleted if any → row permanently deleted.
3. **Session cleanup:** expired session rows deleted.

CORS is restricted to `https://blueandwhitewhs.com`. Real protection comes from
the session-token requirement, not CORS.

## The CMS (`cms/index.html`)

Single-file vanilla JS app. Custom login (NOT Supabase Auth): credentials are
checked by the Worker, which issues a session token. The token is kept in
memory + sessionStorage (`bw_session`) so a page refresh keeps you signed in;
sessions last 12 hours.

### CMS user roles

| Role | Can do |
|---|---|
| Reporter | Write articles, save drafts, submit for review, view own articles |
| Editor | + review queue, publish/return articles, Recycle Bin |
| Adviser | + Staff Manager, staff page publishing, Assignments, All Articles |

### Publish flow

1. Reporter writes → Save Draft / autosave
2. Submit for Review → status `pending`
3. Editor opens Review Queue → review pane (can edit all fields, including
   optional **Auto-takedown date** — "+30 days" button, blank = evergreen)
4. **Publish to Site** → CMS sends generated HTML + session token to Worker →
   GitHub → Pages → live (allow up to ~10 min for the CDN)
5. Article shows "comes down [date]" in All Articles if a takedown is set

### Recycle Bin

- "♻ Recycle" (on archived articles) sets status `trashed` + `trashed_at`
- Recycle Bin view shows countdown ("auto-deletes in N days", red ≤ 7)
- **Restore** → back to `archived` (NOT back on the live site)
- **Delete Forever** → immediate permanent delete
- Anything left 30 days is purged automatically by the sweep

### Staff Manager & staff page pipeline

- Each person has a **Profile** panel: title, grade, beats, photo URL,
  staff page section (incl. Leadership), bio, show-on-page toggle
- **⌂ Publish Staff Page** fetches the live staff.html, regenerates the
  leadership grid and roster between the `BW:LEADERSHIP` / `BW:ROSTER`
  marker comments, and pushes via the Worker (adviser only)
- People whose section doesn't map to a page section are reported by name
  in the success toast instead of silently dropped
- Photos render grayscale per the page design; blank photo = initials card
- Removing a student: kills login + their active sessions immediately;
  published bylines survive (stored as text on each article)
- staff.html in the repo must keep its marker comments — the generator
  errors loudly if they're missing

## Security Model (as of June 11, 2026)

**Protected:**
- GitHub token + service key: server-side Worker secrets only
- Site files (GitHub): can only be changed with a valid editor/adviser session
- users + sessions tables: RLS-locked; passwords unreadable by the public key
- Login, staff management, password changes: all server-verified
- Worker no longer takes orders from strangers — every privileged action
  requires a session token

**Known remaining gaps (PHASE 2 — highest-value next security work):**
- The `articles` and `assignments` tables are still READABLE AND WRITABLE with
  the publishable key, which is public (it ships in the site's JS). Practical
  consequences: (a) someone could INSERT/UPDATE a fake "published" row and the
  homepage/section feeds would render it — i.e., client-side defacement of the
  feeds with arbitrary text/images; (b) unpublished drafts and editor notes are
  publicly readable. Cleanup = delete the bad rows; the GitHub-served article
  pages themselves cannot be touched this way.
- Phase 2 design: route all article/assignment WRITES through the Worker
  (session-checked, like staff ops), then enable RLS with anon SELECT limited
  to `status = 'published'` rows and only the columns the public site needs.
- Passwords are stored as plain text (now hidden behind RLS, but proper
  hashing is the eventual right thing).
